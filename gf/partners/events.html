LP8 · Gateway events (note 24 part 2, PartnerEvent; note 27, "Inbound" and "The envelope"). Every message a partner sent (CALLBACK) and every difference the poll found (POLL), logged before anything is acted on. It answers: what did the partner tell us, exactly, when, was it really from them, and what did we do with it? The adapter turns each into canonical events (27), which loans applies.

Status. Applied: the handler changed something. Ignored: valid but changed nothing (a stale status, a repeat). Held: the loan wasn't found yet; retried for 24 hours, then failed. Failed: processing raised an error; flagged for staff (EVENT_FAILED). Rejected: the signature failed (exactly when the signature is invalid, and then the event id is blank), answered 401, never parsed or processed.

Never edited. A trigger keeps the partner, connection, source, event id, partner event, arrival time, signature and raw body fixed; a row is never deleted. Staff with lending_partners.operate (Operations and up) may run a FAILED event again after a fix, and ask the gateway to poll the loan. View only doesn't see the logs.

Order (27). Status events apply only if newer than the last applied (by sequence, then when they happened, then arrival); ledger facts apply in any order. A repeated event id is answered 200 and ignored: its duplicates count goes up.
